# Orbitaly rotator firmware

The Arduino half of the station: `Pi ──USB──▶ Arduino ──step/dir──▶ drivers`.

This firmware is an **exact pulse executor**. It accepts segments — "N pulses in
this direction at this period" — emits exactly that many, and reports exactly
how many went out. It does not know that degrees exist.

That is deliberately the opposite of K3NG-style rotator firmware, and the reason
matters. Firmware that accepts position targets ("go to az 137") has to invent
its own trajectory, re-decides it every time a new bearing arrives, has no
committed queue to replan from, and reports position by its own reckoning that
the host cannot audit. That architecture is why such setups lurch. Here every
trajectory decision is made on the Pi, by code with a test suite behind it, and
the board's only job is to be honest about pulses.

**What it does:** execute segments in order with exact counts · serialise
direction changes (drain, flip DIR, wait `DIR_SETUP_US`) · watch endstops and
the E-stop at interrupt latency, abort locally, and report the exact count at
the cut · manage the enable lines · answer status queries · enforce a bounded
queue with explicit flow control.

**What it must never do:** generate trajectories, ramp, interpolate or smooth ·
accept position targets · guess a position · drop or reorder segments silently ·
move on its own initiative, including "helpfully" backing off an endstop · hold
configuration the host reasons about.

## Files

| File | |
|---|---|
| `orbitaly_rotator.ino` | serial pump, frame dispatch, segment scheduling, watchdog |
| `pins.h` | **the per-build file** — pin numbers, polarity, driver timing |
| `protocol.h` | frame types, versions, payload sizes — single source of truth |
| `framing.{h,cpp}` | SOF scan, CRC-16, encode/decode. No Arduino dependencies |
| `queue.{h,cpp}` | per-axis segment ring. No Arduino dependencies |
| `stepgen.{h,cpp}` | the ISRs; the only file that touches timers |
| `test/` | host-compiled torture test for the two Arduino-free files |

`framing.cpp` and `queue.cpp` avoid Arduino headers *on purpose*, so the parts
that are easy to get subtly wrong — CRCs, byte order, resynchronisation, ring
wraparound — can be tested on a machine with a debugger:

```bash
cd firmware/test
c++ -std=c++11 -Wall -Wextra -I../orbitaly_rotator \
    test_firmware_core.cpp ../orbitaly_rotator/framing.cpp ../orbitaly_rotator/queue.cpp \
    -o test_firmware_core
./test_firmware_core golden_frames.txt
```

`pytest` does this for you when a C++ compiler is present, and skips visibly
when it is not. It feeds both implementations the **same golden vectors** the
Python side uses (`golden_frames.txt`, generated by
`scripts/make_golden_frames.py`), and a separate pytest parses `protocol.h` and
asserts every constant matches `orbitaly/motion/serial_protocol.py`. Two
implementations of one protocol will drift; this is what catches it.

## Board

**Reference target: ATmega328P — Arduino Uno or classic Nano.**

- **Azimuth on Timer1** (16-bit, CTC). A prescaler plus `OCR1A` gives an exact
  period from microseconds to seconds; the only jitter is interrupt latency.
- **Elevation on Timer2** (8-bit) with a software postscaler: a fixed ~64 µs
  base tick and an accumulator decide which ticks become steps. Jitter is
  bounded by the base tick — about 4% velocity ripple against elevation's
  1406 µs reference period, and **zero position error**, which is the same
  trade already accepted for lgpio.
- Timer0 is untouched, so `millis()` still works.
- Ceiling is comfortably 2×2000 steps/s. The reference gearing needs 1600 (az)
  and 711 (el).

Anything hotter — high microstepping, faster gearing — points at a Mega2560
(four 16-bit timers) or an RP2040. The protocol is board-agnostic and nothing
outside `stepgen.cpp` and `pins.h` assumes AVR, but neither port is done.

## Flashing

```bash
arduino-cli core install arduino:avr
arduino-cli compile --fqbn arduino:avr:uno firmware/orbitaly_rotator
arduino-cli upload  --fqbn arduino:avr:uno -p /dev/ttyACM0 firmware/orbitaly_rotator
```

There is no over-the-air update from the Pi, on purpose. Flashing is a
deliberate act you perform at the bench.

The handshake refuses a protocol version mismatch, so a **stale flash fails in
`orbitaly doctor`** — with both versions printed — rather than halfway through
a pass.

## Wiring

Pin numbers are Arduino digital pins, set in `pins.h` and reported back in the
handshake so `orbitaly doctor` prints what the board is actually running.

| Signal | Default pin |
|---|---|
| AZ step / dir / enable / endstop | 2 / 3 / 4 / 5 |
| EL step / dir / enable / endstop | 6 / 7 / 8 / 9 |
| E-stop | 10 |

**Endstops and the E-stop are normally closed to ground**, inputs pulled up.
Released reads 0; pressed reads 1 — and so does a cut wire, a corroded
connector, or an unplugged switch. Every wiring failure reads as "at the limit"
rather than "clear sky". Do not switch to normally-open because the idle level
looks tidier.

Grounds must be common between the Arduino, the drivers and the motor supply.
The Arduino's 5 V will not run motors; the drivers take their own supply.

### The auto-reset gotcha

Opening the serial port asserts DTR, which **resets the board** into roughly two
seconds of bootloader silence. This is normal and the host handles it: it waits
for the boot `IDENT` before handshaking, and `rotator.serial.connect_timeout_s`
covers the delay.

An `IDENT` arriving *mid-session* therefore means something else — a brownout, a
watchdog, a replugged cable. The host treats it as what it is: the firmware's
queue is gone, so every segment it had accepted but not reported is unaccounted
for, both axes drop `homed`, and re-homing is demanded before anything moves.
The link itself is re-established automatically, because a station that needs a
human to restart a process after a brownout is not one you can leave running.

If the reset is a nuisance on your bench, a 10 µF capacitor between RESET and
GND suppresses it (remove it before flashing). The software never assumes you
have done this.

## Commissioning

Motors disconnected from the mechanism first, every time.

```bash
orbitaly doctor                 # finds the port, prints firmware version and pinout
orbitaly selftest --serial      # latency, flow control, resync, step accounting
```

`selftest --serial` proves the **link** and the firmware's step **accounting**.
It does not prove the pulse train itself — only a scope on the STEP pin can do
that, and the tool says so rather than letting you assume otherwise.

Then follow the commissioning order in `docs/HARDWARE.md`: driver current,
homing with the gearbox uncoupled, endstop check, then travel limits.

## The protocol, in brief

Binary, framed, CRC-checked, 115200 baud:

```
0xA5 | len (u8) | type (u8) | payload | crc16-ccitt (le, over len..payload)
```

Message types have their high bit set when the firmware is the sender, so
wrong-way traffic on a loopback is recognisable rather than plausible. The host
sends `HELLO`, `SEG`, `ABORT`, `ENABLE`, `CLEAR_FAULT`, `PING`, `STATUS`; the
firmware answers `IDENT`, `ACK`, `NACK`, `DONE`, `ABORTED`, `EVENT`, `STATE`,
`PONG`.

Three properties are worth knowing because the rest of the system leans on them:

- **`ABORTED` carries an exact executed count.** lgpio cannot say how many
  pulses of a cut train reached the motor, which is why an abort there loses
  the position reference. A microcontroller counts its own ISR ticks, so an
  endstop hit no longer costs a re-home. An E-stop still does — not because the
  count is unknown, but because it drops the enables, and an unpowered stepper
  under wind load holds nothing.
- **Re-sends are idempotent.** The firmware re-ACKs a sequence number it has
  already accepted instead of executing it twice, which is what makes CRC
  recovery safe for position.
- **A full queue is refused, never silently dropped.** A dropped segment is a
  position error the host would have no way of learning about.

Full field layouts: `protocol.h` and `orbitaly/motion/serial_protocol.py`.
